| 领域 | 方案 | 原因与边界 |
| --- | --- | --- |

| Manager 部署 | 一个小型 C# 部署组件、稳定的 Manager 启动器及完整版本目录 | 安装器与更新器共用激活／恢复协议；不添加 Rust 管理层或新 UI 框架 |

微软支持将完整的非打包、自包含目录放入自定义安装器。.NET 与 Windows App SDK 依赖都必须包含；WinUI 单文件可执行程序不是本方案的交付目标。[微软部署指南](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps)。

Inno 7.1.0 x64 已固定在 `packaging/windows/inno-toolchain.json`，工具脚本验证官方下载摘要及发布者后安装到忽略的 `target/toolchain`。继续支持直接命令，mise 提供可选别名。[官方下载](https://jrsoftware.org/isdl.php/Inno-Setup-Downloads)。

如有企业部署需求，再考虑 WiX/MSI/Burn。MSIX/Store 需要单独验证包身份、共享数据和卸载行为。Velopack 保留为备选实验：其默认目录可能与现有数据根目录冲突，Windows 更新器也可能尝试终止锁定当前目录的进程。它不能代替我们的数据、Runner、信任和进程策略。[Velopack Windows 生命周期](https://docs.velopack.io/packaging/operating-systems/windows)。

## 安装布局与所有权

已交付的默认 Manager 程序位置与稳定数据位置相互独立。首次安装可选择本地固定磁盘上另一个经过验证的空目录：

```text
%LOCALAPPDATA%\Programs\SteamWrapper\
  SteamWrapper.exe                 # 已实现的 Manager 专用启动器
  installation.json               # 已验证的当前／上一安装状态
  versions\<release-tag>\          # 一个完整、不可变的 Manager 目录
    SteamWrapper.Manager.exe
    ...运行时、原生及本地化资源...
    Runner\SteamWrapperRunner.exe  # 随包资源，不是 Steam 的启动目标

%LOCALAPPDATA%\SteamWrapper\
  profiles.toml
  ui-settings.json
  bin\SteamWrapperRunner.exe       # 不变的稳定 Steam 启动目标
  updates\trust-state.json         # 保留序号／摘要／时钟状态；仅更新底层使用
  logs\, backups\, cache\
    cache\updates\<transaction>\  # 受限下载及一次性辅助程序工作区
```

稳定启动器只启动 Manager。它不会出现在 Steam 启动项中；日常游戏仍使用稳定的 Rust Runner，无需 Manager、启动器、更新器或联网检查。安装状态与游戏配置、界面偏好分开保存。

首次安装允许选择本地固定磁盘上经过验证的空目录，默认使用上面的程序位置。每用户 AppId 和登记位置共同标识安装，升级和修复留在原处。开始菜单快捷方式默认开启、桌面快捷方式默认关闭，完成后可打开 Manager。不添加服务、计划任务、开机启动项或 HKLM 写入。快捷方式指向稳定启动器；Manager 保持一致的 AppUserModelID，以保留任务栏固定项。本机静默进程步骤、限定英／中原生流程及私有无 SDK 候选生命周期已通过；[测试](/SteamWrapper/zh-cn/development/testing/)区分各自产物、夹具重试与剩余验收。

设置 `PrivilegesRequired=lowest`、`CloseApplications=no` 和 `RestartApplications=no`。安装／更新要求已有 Manager 实例完成保存并正常退出，绝不强杀它们或游戏。Inno 默认的应用关闭行为不符合本项目策略，静默模式也不例外。[权限](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm)、[应用关闭](https://jrsoftware.org/ishelp/topic_setup_closeapplications.htm)。

首版目标限制为真实 Windows 11 24H2 x64；ARM64 仿真和更早的 Windows 是独立目标。安装、恢复和卸载文本需同时提供完整英语／简体中文，并包含标准图标、许可证／声明材料，以及保留数据的清晰说明。

## 统一部署事务

已实现的源码边界为：`packaging/windows/` 保存 Inno 定义，`apps/deployment-windows/` 保存共享 C# 部署逻辑和 NativeAOT 启动器／辅助程序，恢复时无需加载被替换的 Manager。版本保留／清理及限定范围的快捷方式／注册项恢复已实现并通过测试。跨实例正常退出请求和完整断电恢复仍为独立工作；占用中的操作会被拒绝，提示用户正常关闭 Manager。

Inno 管理安装／卸载入口、注册项及快捷方式，并将输入文件解压到临时工作区。部署组件拥有稳定启动器及清单跟踪的暂存／版本目录。Inno 的 `[Files]` 卸载日志不会自动跟踪其他进程重命名后的暂存目录，不能依靠它删除转为正式版本的目录。安装与卸载钩子必须明确向共享组件交接所有权和锁的生命周期，包括注册项／快捷方式失败时的处理。

安装器、手动修复和应用更新调用同一个部署协议；卸载遵守其所有权与独占锁规则：

1. 验证选定安装包、版本、已安装文件所有权及兼容的部署协议。修改前检查磁盘空间，拒绝不安全根目录或重解析点。
2. 将完整新载荷写入同一卷上的全新暂存目录。验证每个声明文件、本地化资源、运行时、随包 Runner 及最终已签名字节摘要。保持当前版本不变。
3. 激活前取得每用户独占安装锁。启动器与所有 Manager 实例从最早启动阶段到正常退出都参与此锁协议。激活期间阻止新 Manager 启动，并等待已有实例及配置／设置写入结束。只检查一次互斥量仍存在竞态。
4. 写入大小受限的事务日志，将已验证目录转为正式版本，并原子替换安装状态文件中的当前／上一版本。只有部署组件写入此状态；Inno 和更新器不另行实现独立引擎。
5. 释放安装锁，通过启动器启动 Manager。正常初始化后接收与本次事务绑定的健康确认，不自动迁移配置。
6. 通过独立的短期写入锁，在本次事务绑定的日志记录中标记健康；这既不改变当前版本指针，也不将新 Manager 生命周期内持有的共享锁升级为独占锁。需要独占安装锁的清理／压缩延后至下一次安全安装或修复。只有当前版本确认健康后，才清理清单明确归属的旧程序文件，保留当前和记录中的上一版本。存在上一版本指针不代表该旧 Manager 已成功初始化。

版本准入上限为 32 个目录及 32 MiB 所有权日志。安装后可以暂时保留三个版本，等待下一次安全清理。卸载允许在相同日志大小限制内处理最多 1,024 个旧版本，不递归清空未知文件或恢复隔离目录。版本保留测试及真实冻结旧辅助程序恢复夹具已通过；旧版本夹具中的合成载荷与模拟健康确认不证明旧 Manager 界面启动。实现保留旧日志／状态契约，不改写历史安装元数据。

原子替换一个状态文件，**不能**证明整个安装器、注册表、快捷方式和断电事务均具备原子性。事务日志恢复、首次安装与启动器自身更新必须有真实故障测试。启动器运行时无法被替换；应拒绝／延后，不安排重启时强制替换。更新辅助程序从已验证的独立缓存位置运行，避免覆盖自身可执行程序。

若新 Manager 在健康确认前退出，只有重新取得独占锁并确认数据／Runner 兼容后才能恢复上一版本指针。仍在运行但启动较慢的 Manager 不代表失败：报告超时并提供恢复入口，不终止它，也不自动启动与其竞争的另一版本。首版可以承诺已验证的手动恢复；无人值守启动回滚是以后需要独立证据的能力。

## 稳定 Runner 与卸载

Manager 安装／更新拥有随包资源，不替换稳定 Runner 或数据目录。现有 C# `RunnerInstaller` 继续负责共享 Runner 安装、清单／哈希识别及原子二进制替换。Manager 安装本身不写 Steam 启动项；下述明确选择的卸载清理是移除操作的唯一限定例外。

旧 Runner 与配置契约兼容时，只更新 Manager 可以在游戏继续运行期间进行。稳定 Runner 的替换应延后至安全时机，不为释放其文件而强杀游戏。当前安装服务具备文件占用处理，但没有完整的启动与更新生命周期协议。宣称可协调这两者前，应增加经过测试的跨进程 Runner 锁协议，并保留旧受支持 Runner 及其恢复行为。旧 Runner 不参与新增锁协议：在该兼容阶段仍保留原子替换及 Windows 对占用文件的拒绝行为，不能仅因升级 Manager 就宣称协调没有竞态。不兼容时阻止安装，或要求独立审核的迁移；首版更新器只支持现有配置／CLI 契约。

默认卸载只删除归属明确的 Manager 版本、启动器、快捷方式及卸载注册项，保留独立数据。卸载持有同一个独占安装锁，直至文件删除及 Inno 注册项／快捷方式移除完成。已验证的卸载辅助程序运行在待删除目录之外。真实隔离 Inno／辅助程序进程测试及私有无 SDK 生命周期覆盖了这项交接，不代表全部生产故障组合均已验证。

七个独立且默认关闭的选项分别移除可识别的 SteamWrapper 启动选项、下载缓存、日志、Manager 偏好、配置、精确识别的配置备份或经过验证的稳定 Runner 文件。还原要求 Steam 已退出，先备份受影响的账号文件，只清空匹配稳定 Runner／AppID 的标准生成命令，保留其他字节并拒绝并发修改。自定义命令不改，清空命令也无法恢复未知的历史参数。删除配置／Runner 还要求全部本地账号可读且没有残留 Runner 引用。删除 Runner 持有其安装锁，并根据受支持的侧车或按哈希命名的元数据校验实际字节；配置、设置和缓存清理遵守对应写入锁。

未知或被占用的文件、Steam 恢复备份与 `updates/trust-state.json` 继续保留。任何选项都不碰游戏／存档，不跟随链接，不递归清空目录。清理可以报告有文件保留，不会将部分完成说成全部数据已删除。冻结 `0.2.6` 安装器逻辑的九项真实清理选择已通过；快捷方式与注册项恢复的单独记录片段通过，原组合测试仍保留为失败。限定英／中原生取消、缓存清理及默认卸载结果也各自记录。这些结果不证明生产 `0.2.7` 的全部清理、语言或故障组合。[Inno 卸载删除指引](https://jrsoftware.org/ishelp/topic_uninstalldeletesection.htm)。

便携版改用安装版时，不复制游戏文件，并保留现有数据／稳定路径。不提供原地迁移位置：先卸载 Manager 并保留数据，再安装到新的空目录。修复保留未知数据及更新且兼容的 Runner；自选目录、任务栏固定项及仅卸载 Manager 后重新安装分别验收。

## SignPath 申请与发行信任

被拒绝的 Foundation 申请及已准备的服务方工具记录在[代码签名政策](/SteamWrapper/zh-cn/project/design/code-signing/)中。这些草案保留供以后选择服务方时使用；当前没有服务订阅或生产 Authenticode 签名。

当前 Setup 和项目自有 PE 文件在 Windows 意义上仍未签名。签名更新清单让 SteamWrapper 验证对应的准确字节，不会生成受 Windows 信任的发布者身份或消除系统提示。有效 Authenticode 签名也不保证完全没有 SmartScreen 提示。[微软指引](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)。

## 签名顺序与版本规则

当前发布顺序为：构建并测试完整载荷，打包 Setup 与 ZIP，发布并下载核验不可变的版本附件，然后签署和发布独立更新索引。七附件的第 2 版产物仍明确为 `signed=false`；旧便携版契约不变。

`packaging/windows/update-trust.json` 仅保存 ECDSA P-256 公钥。`Initialize-UpdateSigning.ps1` 在内存中生成私钥，通过 `gh` 标准输入直接写入仓库密钥 `STEAMWRAPPER_UPDATE_PRIVATE_KEY`，拒绝替换已有信任配置。PR/main 测试使用临时测试密钥，只有版本发布与元数据续期获得正式签名密钥。这验证的是项目更新源及其绑定的安装包摘要，不是 Windows 发布者身份。

每个新构建的可安装载荷都递增统一数字版本，包括 Manager、Application、Deployment、Host 和 Rust 产品。同版本不同字节与静默降级继续被拒绝。不移动已公开的版本标签或覆盖其附件。如果未来加入 Authenticode，使用新的未发布基础版本，先签自有 PE／卸载器再生成最终 Setup，签名后重新生成 Runner 清单，并保留上游签名。现有 `WindowsSigning.ps1` 及服务方草案供该可选路径使用。

轮换密钥时，先用旧密钥发布一个已信任新公钥的客户端，然后才切换发布密钥。唯一签名密钥丢失时，需要手动下载新客户端。仓库权限与密钥保管由维护者负责，不由证书机构管理。

## 可选更新行为与认证

玩家使用**检查更新**，下载提示的新版本后确认安装。自动检查默认关闭，启用后仅在 Manager 打开期间运行；手动检查不会开启自动检查。关闭或取消会结束当前请求，日常从 Steam 启动游戏永远不会检查更新。更新通道跟随当前安装版本；下载源默认自动，在展开的来源选项中可选 GitHub／CNB。

固定的官方 `update-preview`／`update-stable` Release 保存 `SteamWrapper-update.json`。程序先验证封套中原始载荷字节的签名，再解析第 2 版产品／通道／版本／契约字段、安装包 SHA-256／长度及可选 CNB 地址。只接受已配置的项目公钥和固定官方仓库路径。来源缺失、无效签名、重放、元数据过期或时钟回退属于失败，不能显示为“已是最新版本”。序号／时钟状态保留在可清理缓存之外；只有核验对应安装包后才公布 CNB 镜像。

所有请求与重定向采用明确的 HTTPS 主机白名单，不携带凭据或 Cookie。元数据最多 512 KiB，安装包最多 512 MiB，最多五次重定向。下载支持取消，限制时间／长度／摘要，并使用有配额的 `cache/updates/`，为一次性辅助程序保留少量空间。未知文件和重解析点被保留或拒绝，仅识别出的非活动更新文件可清理；不接触配置、封面、Steam 或游戏文件。

安装版 Manager 完成玩家的保存／放弃选择，启动已验证的现有部署 Host 副本，再正常退出。Host 等待该准确进程退出，再次验证并锁定安装包，运行显示进度且不允许重启／强制关闭程序的 Inno，核对已激活版本后重新打开 Manager。其他 Manager 实例可能阻止安装，需正常关闭后重试。保留现有日志／修复／回退规则，不宣称无人值守回退或游戏进程协调。便携版提供版本下载页及新目录解压指引，不自动覆盖任意目录。

## 发行工作流变更

普通合并运行 CI；版本标签构建并发布应用包。手动运行仍只生成预览产物。不可变的七附件 Setup／portable 发行契约和完整发布门禁保持不变。

GitHub 公开发布及可选 CNB 镜像核验后，独立 job 向滚动更新 Release 发布项目签名元数据。每周工作流将此前已验证的索引续期 28 天，不选择新二进制、不重建软件。发布和续期共用并发组；续期保留准确的发行身份与安装包摘要，只递增序号。只有该专用元数据附件可变，版本安装包始终不可变。

GitHub 为主源；CNB 现为 `v0.2.7` 已验证的二进制镜像与签名更新源备用来源。CNB 需要标签同步及版本发布写权限；发行操作优先使用 CNB_RELEASE_TOKEN，也可复用具有相应权限的 CNB_GIT_TOKEN；只有源码的镜像不是下载源。跳过或失败的二进制镜像不能在签名索引中被标成可用。客户端不包含密钥凭据。修改源码、配置公钥或本地测试通过本身不证明公开更新源已经可用；当前发行另有匿名公开核验证据。
